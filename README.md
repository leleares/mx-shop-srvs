### 分布式锁
锁是操作系统给予的资源调度的能力，对同一台服务器上的并发请求使用锁可以很好的解决资源竞争问题。但是一旦统一服务部署为多台服务器，各个服务器之间都有各自的一把锁，无法对同一资源进行很好的并发资源控制，分布式锁就是解决这个问题的，可以理解为抽象于各个服务器之上的一把锁，各个服务共享。

常见的分布式锁实现方案
- 基于Mysql的悲观锁、乐观锁
- 基于redis的分布式锁
- 基于zookeeper的分布式锁

MySql悲观锁：
我很悲观，总是认为数据资源会有人来抢，所以趁早把资源锁住。（MySql语法支持）
注意：悲观锁在MySql中属于行锁，即会锁住一条记录，但前提是for update的查询条件字段是有索引的，如果没有索引，就不是锁一条记录了，而是会升级成表锁。
```sql
START TRANSACTION;

SELECT stock
FROM inventory
WHERE good_id = 1 //注意good_id一定为加了索引的字段
FOR UPDATE; // 这里就把 good_id = 1的这条记录上锁了

UPDATE inventory
SET stock = stock - 5
WHERE good_id = 1; 

COMMIT; // 释放锁
```

### 基于redis的分布式锁
流程：连接redis获取redis client，通过redis client创建连接池pool，使用第三方库redsync基于pool创建mutex，在竞争资源操作前lock，操作完unlock。
原理：拿商品421举例子，当对商品421进行加锁时，会在redis中创建一个标志位，假设为421设置为1，当另一个进程也想对商品421进行操作时，通过查询redis发现该商品已经被锁上，则等到锁的释放才能操作。
核心原理1:【setnx】｜对商品进行加锁时，本质上是两步操作，第一步是查询421在redis中的状态（get），第二步才是设置421在redis中的状态（set），既然是两步操作，高并发场景下就容易被中断，导致锁机制混乱，因此需要一个原子操作，这就是redis的setnx，该操作直接对421进行设置，如果421不存在则设置成功，否则设置失败。
核心原理2:【延时】｜ 想象这样一个场景，如果某个线程获取到锁之后，在释放锁之前挂机了，那么这个锁将无法释放，那么其他线程将无法拿到资源操作的权力，解决方案就是给421这个redis的key加一个过期时间假设为8s，但是要是我正常的业务逻辑就执行了9s，那就是在我正常逻辑执行结束前锁就释放了，别人就拿到了，那锁机制又混乱了，解法就是在正常逻辑结束前去进行刷新过期时间，这个redsync库支持。不过仍然有问题，假想某个进程有bug，不会终止，那她一直刷新redis的key的过期时间别人永远也别想拿到资源的权力。
核心原理3:【安全性】 ｜ 锁只能被锁住的人解开，这是通过redis的key里面的value实现的，设置锁的人会往421这个key中写入一个唯一的value，解锁时再拿这个值去跟redis中的key对应的value做对比，如果是就能解开。
核心原理4:【redlock 红锁】 ｜ redis服务通常不是单一节点，通常是集群，那就会有一个master节点和多个slave节点，正常情况下，master节点会确保所有redis服务中数据的一致性，例如请求g1在redis1中写入了421的状态，g2请求的事redis2中421的状态，可以正常获取到，但是异常是在所难免的，例如master宕机或者网络有异常这会导致很多问题发生。红锁的解决办法就是，所有进程拿锁时必须到所有redis服务的锁（把这些redis服务器都看成是平级）才算拿锁成功，如果有并发，假设存在5个服务器，比如一个进程拿到2个服务器的锁，另一个进程拿到三个服务器的锁，那就拿的多的获取锁，拿两个那个进程需要释放锁。

### 订单服务需要解决的两个重大问题
先设想一个场景：用户下了单 -> 扣减库存 -> 订单表插入一条记录。这是用户购买商品下单所走的基本流程。
问题1？
先扣库存还是订单表里先插数据？
都有问题：
1. 如果先扣库存（调用库存服务）完成后，如果订单服务挂了，插入订单表数据失败，则库存也会滚不了（跨服务无法回滚）。
2. 如果订单表先插数据，插入成功了，扣减库存服务也成功了，但是库存服务响应式服务抖动返回了异常，于是认为库存没扣除成功，回滚了订单表数据插入，这时依然数据不一致。

核心解决方案是：能否采用一种方式，保证订单插入数据和库存扣减的一致性。🌟解决上面问题需要用到分布式事务。

### 事务
事务分两种：本地事务（靠sql的事务的能力），分布式事务（跨服务事务）
四大特性：
原子性。
一致性：事务的中间状态对其他事务不可见。
隔离性：各个事务相互隔离，无法看到别的事务的中间状态。
持久性：是事务的保证，内存的数据应持久到硬盘中。

分布式事务本质上就是多个本地事务。

### 分布式事务基石：CAP理论
C(consistency)一致性：“all nodes see the same data at the same time”，即更新操作成功并返回客户端后，所有节点在同一时间的数据完全一致，这就是分布式的一致性。一致性的问题在并发系统中不可避免，对于客户端来说，一致性指的是并发访问时更新过的数据如何获取的问题。从服务端来看，则是更新如何复制分布到整个系统，以保证数据最终一致。

A(Available)可用性：可用性指“Reads and writes always succeed”，即服务一直可用，而且是正常响应时间。好的可用性主要是指系统能够很好的为用户服务，不出现用户操作失败或者访问超时等用户体验不好的情况。

P(Partition Tolerance)分区容错性：即分布式系统在遇到某节点或网络分区故障的时候，仍然能够对外提供满足一致性和可用性的服务。分区容错性要求能够使应用虽然是一个分布式系统，而看上去却好像是在一个可以运转正常的整体。比如现在的分布式系统中有某一个或者几个机器宕掉了，其他剩下的机器还能够正常运转满足系统需求，对于用户而言并没有什么体验上的影响。
如果你你是一个分布式系统，那么你必须要满足一点：分区容错性。

🌟取舍策略：CAP三个特性最多只能同时满足两个，那就有三个策略。

事实上：C和A是互斥的。想要满足一致性，意味着必须加锁通过控制访问来实现，但加锁就意味着不可访问。

### Base理论
Base理论总的来说强调一种折中状态。即允许暂时不一致，但最终能达到一致状态。
比较经典的例子就是支付宝转账。A给B转账，系统会提示转账最长可能需要两个小时才能完成，这就是不一致的表现（A减了但是B没加），但系统给了友好提示用户是可以接受的。倘若强一致，即对外完全暴露A没减，B没增和A减了，B增了这两种状态，则必然会影响高并发系统的可访问性。

BASE是Basically Available（基本可用）、Soft state（软状态）和Eventually consistent（最终一致性）三个短语的缩写。BASE理论是对CAP中一致性和可用性权衡的结果，其来源于对大规模互联网系统分布式实践的总结，是基于CAP定理逐步演化而来的。BASE理论的核心思想是：即使无法做到强一致性，但每个应用都可以根据自身业务特点，采用适当的方式来使系统达到最终一致性。接下来看一下BASE中的三要素：


1. 基本可用
基本可用是指分布式系统在出现不可预知故障的时候，允许损失部分可用性—-注意，这绝不等价于系统不可用。比
如：
（1）响应时间上的损失。正常情况下，一个在线搜索引擎需要在0.5秒之内返回给用户相应的查询结果，但由于出现
故障，查询结果的响应时间增加了1~2秒
（2）系统功能上的损失：正常情况下，在一个电子商务网站上进行购物的时候，消费者几乎能够顺利完成每一笔订
单，但是在一些节日大促购物高峰的时候，由于消费者的购物行为激增，为了保护购物系统的稳定性，部分消费者可
能会被引导到一个降级页面

2. 软状态
软状态指允许系统中的数据存在中间状态，并认为该中间状态的存在不会影响系统的整体可用性，即允许系统在不同
节点的数据副本之间进行数据同步的过程存在延时

3. 最终一致性
最终一致性强调的是所有的数据副本，在经过一段时间的同步之后，最终都能够达到一个一致的状态。因此，最終一
致性的本质是需要系统保证最终数据能够达到一致，而不需要实时保证系统数据的强一致性。总的来说，BASE理论
面向的是大型高可用可扩展的分布式系统，和传统的事物ACID特性是相反的，它完全不同于ACID的强一致性模型，
而是通过牺牲强一致性来获得可用性，并允许数据在一段时间内是不一致的，但最终达到一致状态。但同时，在实际
的分布式场景中，不同业务单元和组件对数据一致性的要求是不同的，因此在具体的分布式系统架构设计过程中，
ACID特性和BASE理论往往又会结合在一起。
一句话：CAP就是告诉你：想要满足C、A、P就是做梦，BASE才是你最终的归宿

### 常见分布式事务解决方案
• 两阶段提交（2PC, Two-phase Commit）比如调用了库存服务执行扣减操作，那么库存服务本地不真正执行扣减行为，而是本地开启一个事务来等待确认扣减，等订单服务什么都处理完了确保整个链路没问题才执行真正的扣减。缺点就是导致各个系统性能下降的比较厉害。
• TCC 补偿模式 将一个真行执行的动作分成三个动作（try confirm concel），例如调用库存服务，先执行try操作通过在数据库中添加额外字段例如freeze、status这样的字段来表示其pendding状态，等待后续调用confirm或者cancel来真正对数据进行写入操作。缺点非常明显：代码侵入性极强。
• 基于本地消息表实现最终一致性 在订单服务维护一张消息表，调用库存服务不直接打到订单服务而是往表里写数据，本地也启动一个定时服务，定期扫描本地的消息表执行任务，这种情况可以保证最终状态是一致的（因为一次扫描不成功可以继续扫描重试）。
• 最大努力通知：字面意思，一般是主系统将大量消息写入到mq，然后由一个独立的通知系统定时通知到别的系统。
• 基于可靠消息最终一致性方案：基本思路和机遇本地消息表差不多，但是该方案不在本地维护消息表，而是将消息往rocketmq中写入，然后由订阅方（如库存服务）进行消费执行响应扣减库存等操作。这里面有几个核心知识点：1.如何确保订单服务将消息写入到rocketmq中了？rocketmq提供了事务消息，即mq发送方（订单服务）首先会向rocketmq发送一个half消息（无法被mq消费方消费的消息，类似于探活消息）请求rocketmq确认，mq会给发送方发送确认消息，当订单服务本地相关事情处理完之后，再向mq中此消息发出commit/rollback，commit了之后mq消费方才可以进行消费。 2. 如何确保commit/rollback消息mq能收到？rocketmq提供了回查机制，即发现mq发送方好久没动静就会主动向mq发送方询问那条消息到底要commit/rollback。https://piccdn2.umiwi.com/fe-oss/default/MTc3NTI4OTMyMTQ0.png


### Mq（Message queue）
mq即消息队列，是一种先进先出的数据结构，在实际开发中，将其理解为一个组件。

主要有两个作用：1. 解耦 2. 异步  3. 消峰
解耦：假设A服务需要调用B、C、D三个服务，不用MQ代码耦合比较严重，扩展困难。有了MQ以后只需 A -> MQ ->下游服务。这样下游服务可以独立扩展，只需订阅感兴趣的消息即可。
异步：很容易理解，将一些收尾操作，例如通知，下发积分等操作直接往MQ中塞，将这些行为变成异步的即可，由相应的服务去进行一个调用来完成具体业务。
消峰：假如A系统在繁忙时会有巨大的并发，可在A系统前增加一个MQ，所有请求将打到MQ当中，又MQ批量将请求交给A系统。

### Mq基础概念
• Producer：消息的发送者；举例：发信者
• Consumer：消息接收者；举例：收信者
• Broker：暂存和传输消息；举例：邮局

多个Topic消息
• Tag：区分消息种类的二级细粒度分类
• Message Queue：相当于是Topic的分区；用于并行发送和接收消息 （只需关注他是存储消息的即可，一般不会直接操作他）

### RocketMq 消息类型
按照发送方式分类：
1. 异步发送：向MQ发送消息同时等待其响应，如果发送失败则进行重试，最多重试两次，注意这个是阻塞线程的。
2. 同步发送：向MQ发送消息然后就不管了，但注意发送MQ的线程不能立马关闭，MQ会有回调通信之类的。
3. 单向发送：向MQ发送消息彻底不管了，适用于允许部分消息丢失的情况。

按照消息类型分类：
1. 普通消息：最普通的消息，生产者向消息队列发送消息，消费者消费消息，不保证顺序（虽然mq是队列，但由于有很多broker，这些消息可能放到了不同的broker，就导致取得时候没顺序了）
2. 顺序消息：要想保证顺序，消息只能往同一个broker中放数据，取数据也只能从一个broker中取数据，这势必会造成并发下降。
3. 延时消息：指的是可以想mq中发送一个指定定时时间的延时消息，到时间了这个延时消息才能被消费。
4. 事务消息：本质为了解决：“本地事务执行成功，但消息发送失败” 或 “消息发送成功，但本地事务失败” 的不一致问题。RocketMQ 事务消息通过“半消息 + 本地事务 + 状态回查”的机制，实现了分布式场景下的最终一致性。生产者先发送半消息，再执行本地事务，根据执行结果提交或回滚消息。如果状态不确定，Broker 会主动回查，从而避免消息丢失或业务不一致。

### 服务雪崩
指的是由于底层服务宕机或者响应速度极慢，导致调用该服务的服务宕机，从而导致整个服务集群宕机。
解决服务雪崩必须引入的机制：超时机制、重试机制、幂等性保证。

超时：指定请求超时时间，超过这个时间则自动timeout。
重试：请求服务超时后，能否请求该服务的其他服务器，其他服务器的并发压力可能小点儿，请求响应成功的概率也更大。
幂等：对于读数据，一般多次请求是没有问题的，但对于写数据，由于各种原因调用了两次或者n次竟然在库里写了n份数据，或者对于同一个一次性付款码竟然能支付多次，这就是幂等性要解决的问题。

幂等性
哪些接口需要考虑幂等性：一般是对于post请求，以及部分put和patch请求需要考虑，对于纯查询接口是不需要考虑的。（某些post、patch、put请求同样不需要考虑幂等性，例如将某个商品价格改为200，一次跟两次请求没有区别）

常见幂等性解决方案：
1. 唯一索引（或者联合唯一索引）。就拿用户注册这件事来说，假如同一个入参同时请求了多次，但由于mobile字段是唯一索引，这样无论相同入参请求多少次都不会重复创建相同用户。
2. token机制。很多场景下，表中是无法设计唯一索引的的，例如商品表中允许相同名称、相同价格、等字段相同，那如何区分用户是在同一个session页面点了n次，还是不同用户提交了一个一模一样的请求呢，这时就需要前端在页面中自己生成一个唯一token，后端拿到这个token后，首先在redis中查询是否有这个token，如果没有证明没处理过则处理之，如果有则证明处理过了无需再处理。
3. 幂等表。 多整一张表（id唯一），用于记录更新或者插入情况，请求来之前先向这个表中insert数据，能insert成功代表没处理过这个请求，insert不成功代表处理过这个请求。
4. 基于状态机的条件更新。表中加一个字段status，表示该记录是否更新过：INIT → PROCESSING → SUCCESS / FAIL，更新时就可以 UPDATE order SET status = 'SUCCESS' WHERE order_id = ? AND status = 'PROCESSING'

### 链路追踪技术 
对于微服务架构，一个api请求可能设计多个服务的相互调用，如果这个api异常了，排查问题只能逐个服务观看日志分析原因，效率低下。
有了链路追踪，可以为这个api请求分配一个唯一的traceId，在整个微服务体系中的每一跳都会记录耗时等情况，还能将这些数据可视化。也就是说只要能拿到traceId，则可以排查各个服务的调用情况，排查问题更容易。
